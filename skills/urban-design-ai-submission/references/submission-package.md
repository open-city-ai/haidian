# Submission Package Contract

The package is a formal structured urban design deliverable generated by an AI agent. The validator treats files in this order of authority:

1. `geometry/*.geojson`
2. `metrics.json`
3. `standard_matrix.json`, `design_depth_matrix.json`, `compliance_matrix.json`
4. `manifest.json`, `sources.json`, `assumptions.json`, `self_check.json`
5. `proposal.md`
6. `assets/figures/*.png`
7. `report/proposal.html`
8. `drawings/*.pdf`
9. `visual/index.html`

`proposal.md` is the only main human-readable proposal. It must explain the design, cite machine evidence with `[source:...]`, `[standard:...]`, `[depth:...]`, `[data:...]`, and `[metric:...]`, and embed local figures from `assets/figures/`. `report/proposal.html` is the rendered offline reading version of the same Markdown. Figures, PDFs, HTML, video, audio, and interactive scenes are presentation artifacts. They help humans review the proposal, but they must not be the only basis for boundary, area, planning-control, or indicator claims.

Rich optional presentation media belongs in `assets/media/`: locally stored video, audio or music, posters, caption tracks, and transcripts. When the Agent has suitable capabilities it should actively use these media, generated images, and locally bundled Three.js/WebGL/Canvas experiences to make the proposal intuitive for people. These do not replace the required five figures, drawings, report HTML, or visual HTML. Declare every file, reference, language, and hash in the manifest. Video needs a poster, VTT captions, and a Markdown transcript; audio needs a transcript; nothing may autoplay. Set optional `cover_image` to a cleared PNG/JPEG/WebP in `assets/media/`, or leave it empty/null/absent to retain the repository-generated cover.

## Required Manifest Fields

`manifest.json` must identify:

- schema, package, project, and site-package versions
- submission stage and type
- agent identity and model inside the `agent` object; use optional `model_family` (`gpt`, `claude`, `deepseek`, `qwen`, `glm`, `kimi`, `grok`, or `other`) plus free-text `model_detail`; replace scaffold placeholders before finalization
- generation timestamp in `generated_at`
- file list with canonical roles and, when written by the finalizer, SHA-256 hashes
- the agent's `validation_claim`, including `self_checked` and `known_blockers`
- optional package type/state, data confidence, and cover image fields where applicable

Every required file path in `manifest.json` must exist and be listed. Hashes should use SHA-256.

## Manifest Field Reference

| Field | Required | Type | Notes |
|---|---|---|---|
| `schema_version` | yes | string | Manifest schema version matching `0.1.x` or `0.2.x` |
| `package_id` | yes | string | Unique slug; typically `<github-login>/<proposal-slug>` |
| `project_id` | yes | string | Must be `centennial-jingzhang-ai-belt` |
| `site_package_version` | yes | string | Version of the site package used; check `brief/` for current value |
| `submission_stage` | yes | string | Legacy depth field; currently `formal` |
| `submission_type` | yes | string | Must be `ai_agent` |
| `agent` | yes | object | Requires nested `agent_id`, `agent_name`, and `model`; optional `model_family` and `model_detail` also belong here |
| `generated_at` | yes | string | ISO 8601 date-time |
| `files` | yes | array | One entry per declared package file (see File Entry below) |
| `validation_claim` | yes | object | Requires `self_checked` and `known_blockers`; may include `data_confidence` |
| `package_type` | no | string | When present, must be `professional_design_package` |
| `package_state` | no | string | Use `ready_for_review` for a completed package; scaffolds use `scaffold` |
| `cover_image` | no | string | Path to `assets/media/` image, or `null`/absent to use generated cover |

The schema sets `additionalProperties: false` at the manifest root. Do not add flattened
fields such as `proposal_slug`, `agent_id`, `submission_timestamp`, or `validation_status`.

### File Entry Shape

```json
{
  "path": "proposal.md",
  "role": "narrative",
  "required": true,
  "language": "zh",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

| Field | Required | Notes |
|---|---|---|
| `path` | yes | Relative to the submission root |
| `role` | yes | See File Role Catalog below |
| `required` | schema 0.2.x | `true` or `false` |
| `language` | no | `"zh"`, `"en"`, or `"neutral"` |
| `translation_of` | no | Set on translation files to reference the primary file path |
| `sha256` | no | 64-character lowercase SHA-256 hex digest of the file content |
| `role_detail` | only for `other` | Stable snake_case description of a non-canonical role |

File entries also use `additionalProperties: false`; `size_bytes` is not a manifest field.

## Computing SHA-256 Hashes

Use the following snippet to generate hashes for all files before writing `manifest.json`:

```python
import hashlib, pathlib

def sha256_file(path: pathlib.Path) -> str:
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()
```

`scripts/finalize_submission.py` computes and writes all hashes when a scaffold is finalized for
the first time. After changing an existing `ready_for_review` package, run
`scripts/refresh_submission_manifest.py` to refresh its declared hashes, then rerun
`scripts/self_check_submission.py --mark-self-checked --json`. Do not rerun the scaffold-only
finalizer or edit hashes by hand.

## Professional Evidence

`standard_matrix.json` maps professional standards to proposal sections, drawings, geometry, metrics, sources, assumptions, and self-checks.

`design_depth_matrix.json` maps formal deliverable depth to the same evidence chain. Required depth items must be `complete`.

The proposal must reference each standard, design depth item, core GeoJSON file, and known metric in readable text. It must also embed these local figures: `site-overview.png`, `land-use-structure.png`, `key-areas.png`, `mobility-bluegreen.png`, and `metrics-evidence.png`. Do not hide the design logic in JSON only.

After editing `proposal.md`, regenerate the reading version:

```bash
python3 scripts/render_proposal_html.py submissions/<agent-id>/<proposal-slug>
```

`report/proposal.html` must be complete offline HTML, must reference the five figures via local paths such as `../assets/figures/site-overview.png`, and must not load remote resources or executable scripts.

## Review-ready Rule

Generated scaffolds, `concept_test`, and drafts are not accepted as participant submissions. A participant must replace the scaffold content and placeholder drawings, remove the draft marker, and run `finalize_submission.py`. If official boundary or key-area geometry is missing, use `brief/site-package/geometry/provisional_boundaries.geojson` only as a clearly labeled `provisional_constraint`. Organizer-supplied data gaps do not block content scoring, but all precision-sensitive metrics must be recalculated when official polygons arrive.

## Unknowns

Use this object shape whenever a value is not available:

```json
{
  "status": "unknown",
  "value": null,
  "reason": "Exact official detailed planning condition was not included in the cleared site package.",
  "required_for_formal_submission": true
}
```

Unknown official controls may be listed as risks or pending professional confirmation. Boundary and key detailed-design areas may be official or provisional; provisional geometry must never be described as official, precise, statutory, or approval-ready.

## HTML Visualization

`visual/index.html` must be a static offline page. It must show the overview map, three scope levels, key areas, land use, traffic/walking, blue-green/public space, buildings/renewal projects, AI scenario nodes, core metrics, compliance coverage, self-check status, sources, and assumptions. Values shown in HTML must match `metrics.json`.
